# Background training deployment gate

This commit is intentionally local-only. **Do not deploy the code before the production database is at `0002_training_jobs`.** The current production baseline is `0001_initial_schema`; never stamp `0002` without applying the migration.

1. Review `alembic/versions/0002_training_jobs.py` and take a verified Neon backup/branch. Test `0001 → 0002` and rollback on a disposable PostgreSQL branch. The automated localhost integration test accepts only `LOCAL_POSTGRES_MIGRATION_TEST_URL` pointing to `localhost/vechar_jobs_test`; it cannot target production.
2. During a controlled deployment window, apply `python -m alembic -c alembic.ini upgrade 0002_training_jobs` to production only after explicit approval. Verify `alembic current` reports `0002_training_jobs` and existing row counts are unchanged. This repository work does **not** perform that operation.
3. Enable Vercel Queues for the backend project and check the `training-plan`, `training-chunk`, and `training-finalize` subscribers from `pyproject.toml` are deployed. The pinned `vercel-queue` SDK uses Vercel-provided identity/OIDC on Vercel; no new application secret or environment variable is introduced for deployed functions. For local Vercel integration use `vercel dev` with a linked project; ordinary local FastAPI uses an in-memory test queue and does not automatically run workers.
4. Keep function duration at the Vercel default unless the current plan and workload justify an explicit override. The application lease is 1,200 seconds, longer than the default 300-second function duration. If a longer function duration is configured later, increase the lease and queue delivery budget together so a live function cannot lose its claim.
5. Deploy and verify a short character/world source, then a multi-chunk source, status polling, usage accounting, and failure/cancellation. Roll back application code only in coordination with migration compatibility.

The job database is authoritative. Messages contain only version and job/chunk IDs. Completed, failed, and cancelled jobs immediately clear their *job artifact* `source_text`; successful finalization also clears intermediate extraction JSON. Canonical `training_sources` / `world_sources` retain their existing raw-text behavior. In particular, `POST /worlds/{id}/extract-character` searches `world_sources.raw_text`, so clearing it would break an existing feature. This canonical-source retention is an explicit privacy follow-up for a separate design/migration; the new job tables do not add a second permanent raw-text copy. Failed jobs retain only safe error codes/messages and metadata.

The endpoints retain their existing paths but now return `202` with `job_id` and `status`; clients poll `GET /training-jobs/{job_id}`. Older synchronous clients expecting a profile in the POST response must be updated before deployment.
